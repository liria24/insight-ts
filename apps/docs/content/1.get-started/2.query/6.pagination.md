---
title: Pagination
description: Continue one canonical result with an opaque, result-local cursor.
---

Pagination belongs to one QueryResult. Results selected in the same `query()` call do not share or
advance pagination state.

```ts
const { overview, errors } = await insight.query((q) => ({
    overview: q.metrics({ metrics: ['requests'], time }),
    errors: q.logs({ time, limit: 32 }),
}))

const cursor = errors.meta.pagination?.next
if (cursor)
    const second = await insight.query((q) => ({
        errors: q.logs({ cursor, time, limit: 32 }),
    }))
```

Only `errors` is queried again, so `overview` does not execute on the second call. QueryResult stays
plain serializable data; it never contains an executable `next()` method.

## Opaque cursors

Pass `meta.pagination.next` back to the same capability with the same logical query. Do not parse,
modify, persist assumptions about, or substitute a Provider-native token for an Insight cursor.
Changing the time range, filters, or limit invalidates the cursor.

The cursor carries the continuation state needed by that result. This can include native tokens,
merged-adapter frontier state, or a History repository position, but those details are intentionally
absent from the public API. At the terminal page, `meta.pagination` is omitted.

## Merged adapters

Logs and Traces merge adapter pages in canonical newest-first order with stable IDs as tie-breakers.
The cursor retains excess rows and each adapter's continuation independently, exposing one logical
`next` value without duplicate or skipped records.

This guarantee assumes each adapter traverses a fixed time range in stable newest-first order. Late
ingestion and Provider-side changes inside that range follow the Provider's consistency model.
Keep the Scope configuration unchanged while traversing a cursor.

The same QueryResult pagination envelope is used for live Provider reads and History-backed reads.
Provider and repository cursor formats never become application API.
