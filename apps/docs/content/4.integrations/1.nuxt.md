---
title: Nuxt
description: Add optional build-time and Nitro runtime integration to a Nuxt application.
---

The Nuxt module connects Analytics SDK to Nuxt and Nitro. It is optional: the core package works in
any server-side TypeScript application.

## Add the module

```ts [nuxt.config.ts]
export default defineNuxtConfig({
    modules: ['@liria24/analytics/nuxt'],
    analytics: {
        name: 'website',
        providers: {
            cloudflare: {
                webAnalytics: {
                    host: 'www.example.com',
                    siteTag: 'your-site-tag',
                },
            },
            googleSearchConsole: 'sc-domain:example.com',
        },
    },
})
```

`nuxt.config.ts` contains declarative resource identifiers and build-time capabilities. Keep
tokens, authorization callbacks, application-state collectors, custom Providers, and custom event
delivery in `server/analytics.config.ts`.

```ts [server/analytics.config.ts]
import { defineNuxtAnalyticsConfig } from '@liria24/analytics/nuxt/runtime'

export default defineNuxtAnalyticsConfig({
    providers: {
        googleSearchConsole: {
            getAccessToken: () => getGoogleAccessTokenFromServerSecrets(),
        },
    },
})
```

Cloudflare Web Analytics credentials are read from private
`runtimeConfig.cloudflare.accountId` and `runtimeConfig.cloudflare.apiToken`, with
`CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` as environment fallbacks.

## Server queries

The module auto-imports `useServerAnalytics()` for Nitro server code. It resolves configured
resource identifiers, runtime credentials, custom Providers, default Sources, and archive storage
before returning the shared Analytics client:

```ts [server/api/traffic.get.ts]
export default defineCachedEventHandler(async (event) => {
    const analytics = await useServerAnalytics(event)
    const to = new Date()
    const from = new Date(to)
    from.setUTCDate(from.getUTCDate() - 7)

    return analytics.traffic.series({
        grain: 'day',
        metrics: ['pageViews', 'visits'],
        range: { from: from.toISOString(), to: to.toISOString() },
    })
})
```

Pass the H3 event so request-scoped platform bindings such as Cloudflare Analytics Engine can be
resolved from the runtime context.

Request-scoped custom Providers receive the H3 event without leaking H3 types into the Core API:

```ts [server/analytics.config.ts]
export default defineNuxtAnalyticsConfig({
    customProviders: ({ event }) => [customProvider({ db: event?.context.cloudflare?.env.DB })],
})
```

## Browser events

Event schema and browser transport are separate capabilities:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
    modules: ['@liria24/analytics/nuxt'],
    analytics: {
        name: 'website',
        events: {
            signupCompleted: {
                properties: { plan: ['free', 'pro'] },
            },
        },
        relay: true,
    },
})
```

- `events` only defines schema and typing.
- `events` with `relay` generates the browser runtime, auto-import, and HTTP route.
- `relay` without at least one event is a configuration error.

```ts
useAnalytics().track('signupCompleted', { plan: 'pro' })
```

## Archive storage

Archive mode requires persistent Nitro Storage:

- `providers.cloudflare.r2` creates an R2 mount at `archive.base`, or at `analytics:archive` when
  no base is specified.
- `archive: { base: 'custom:archive' }` without R2 uses that existing named mount.
- `archive: true` requires an existing `analytics:archive` mount.
- a missing required mount fails the build.

The module never overwrites an existing storage mount.

Use a custom R2 mount name:

```ts [nuxt.config.ts]
analytics: {
    name: 'website',
    archive: { base: 'my-archive', retention: '1y' },
    providers: {
        cloudflare: { r2: 'ANALYTICS_ARCHIVE' },
    },
}
```

This configures the resolved `my-archive` mount with Nitro's `cloudflare-r2-binding` driver. If
`nitro.storage['my-archive']` already exists, the existing configuration wins.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
    modules: ['@liria24/analytics/nuxt'],
    analytics: {
        name: 'website',
        archive: true,
    },
    nitro: {
        storage: {
            'analytics:archive': {
                driver: 'fs',
                base: './.data/analytics',
            },
        },
    },
})
```

Use a persistent platform driver in production. Maintenance correctness lives in
`analytics.maintenance.run()`; the optional Nitro task is only a scheduler bridge.

## Vue UI styles

The default is component-aware CSS injection:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
    modules: ['@liria24/analytics/nuxt'],
    analytics: {
        name: 'website',
        ui: {
            styles: 'auto',
        },
    },
})
```

`auto` scans `.vue`, `.ts`, `.tsx`, `.js`, and `.jsx` source for `AnalyticsStat`,
`AnalyticsLineChart`, or `AnalyticsBreakdownTable`. It generates `.nuxt/analytics/vue.css` and
updates that template during development when matching source is added or removed.

Using only `provideAnalytics()` or `useAnalytics()` does not inject component CSS.

Always inject styles:

```ts
analytics: {
    name: 'website',
    ui: { styles: true },
}
```

Disable injection:

```ts
analytics: {
    name: 'website',
    ui: { styles: false },
}
```

When disabled, import the stylesheet manually wherever appropriate:

```ts
import '@liria24/analytics/vue/style.css'
```

This feature injects CSS only. Vue components remain explicit imports from
`@liria24/analytics/vue`.
