---
title: Architecture
description: The dependency boundaries between core semantics, provider adapters, and integrations.
---

The dependency direction is deliberately simple:

```text
Integration → Adapter → Core
```

- **Core** owns queries, reports, source selection, rollups, events, application state, and
  archive semantics.
- **Adapters** validate provider capabilities and translate provider-native requests and
  responses.
- **Integrations** resolve host configuration and connect runtime primitives such as H3, Nitro
  Storage, and Nitro Tasks.

Core never imports provider or framework code. Adapters import core only and never import Nuxt,
Nitro, H3, or Vue code.

## Provider semantics are data

Reports retain their source, query time, timezone, freshness, sampling, approximation,
threshold, partial-result status, and warnings. Derived metrics such as CTR are recalculated
from supporting values instead of being summed across partitions.

## Explicit source selection

A query can name its source. Without one, the core uses a configured domain default or a single
compatible source. Multiple compatible sources are an error, not a silent choice.

## Archive

Archive storage uses versioned JSON partitions through unstorage. Live and archived coverage is
split at query time, with boundary de-duplication and quality metadata preserved. Integrations use
the runtime's native storage rather than introducing a second storage system.

Archive data is historical materialization, not a result cache. Applications remain responsible
for request-level or response-level caching through their own runtime.

## Optional framework layers

The package surface mirrors the dependency boundaries. The core, provider, Nuxt, Nuxt runtime,
browser, and Vue entries are separate exports. Importing the core does not pull Nuxt or Vue into
the application.
