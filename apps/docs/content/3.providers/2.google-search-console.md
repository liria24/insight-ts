---
title: Google Search Console
description: Understand the Search Analytics Source, authentication boundary, and archive behavior.
---

Google Search Console contributes one `search` Source backed by the Search Analytics API. It is a
read-only provider interface; Analytics SDK does not create OAuth routes, store refresh tokens, or
own a browser tracker.

## Search

The Provider exposes `google-search-console.search-analytics`.

| Type       | Available values                                                             |
| ---------- | ---------------------------------------------------------------------------- |
| Metrics    | `clicks`, `impressions`, `ctr`, `averagePosition`                            |
| Dimensions | `date`, `hour`, `query`, `page`, `country`, `device`, `searchAppearance`     |
| Reports    | Scalar totals, daily/hourly series, and supported dimension breakdown tables |

Clicks and impressions are additive. CTR is recomputed from clicks and impressions.
Average position is impression-weighted and non-additive.

```ts
import { createAnalytics } from '@liria24/analytics'
import { googleSearchConsole } from '@liria24/analytics/google-search-console'

const analytics = createAnalytics({
    name: 'website',
    providers: [
        googleSearchConsole({
            property: 'sc-domain:example.com',
            auth: {
                getAccessToken: () => getGoogleAccessTokenFromServerSecrets(),
            },
        }),
    ],
})
```

The host owns OAuth login, authorization, refresh-token storage, and token refresh. The callback
must return a current access token with the `webmasters.readonly` or `webmasters` scope.

Google Search Console data may be non-public Google user data. If you expose this data to users
other than the Google account that authorized access, you are responsible for obtaining any
required consent and complying with the Google APIs Terms of Service and Google API Services User
Data Policy. Do not assume that application-level admin access alone authorizes disclosure.

Search Analytics pages are fetched sequentially in native pages of up to 25,000 rows. The Provider
preserves requested dimension order, data-state metadata, top-row limitations, and incomplete
coverage warnings.

Search Console uses the `America/Los_Angeles` calendar. Half-open query instants are translated to
provider dates, and reports record that source and bucket timezone. Read requests retry transient
`429`, `500`, `502`, `503`, and `504` responses at most twice while permanent client errors are
returned immediately.

## Archive

The built-in materialization stores daily `clicks`, `impressions`, and `ctr` by date. Initial
maintenance can look back about 16 months. Completed monthly coverage keeps refreshing for seven
days after the partition ends so delayed rows can arrive before it is sealed.

`ctr` is safely recalculated from archived clicks and impressions. `averagePosition` is not in the
built-in materialization because it cannot be safely added across partitions.

## Nuxt configuration

Put the property identifier in `nuxt.config.ts`:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
    modules: ['@liria24/analytics/nuxt'],
    analytics: {
        name: 'website',
        providers: {
            googleSearchConsole: 'sc-domain:example.com',
        },
    },
})
```

Keep the access-token callback in server-only configuration:

```ts [server/analytics.config.ts]
import { defineNuxtAnalyticsConfig } from '@liria24/analytics/nuxt/runtime'

export default defineNuxtAnalyticsConfig({
    providers: {
        googleSearchConsole: {
            getAccessToken: () => getGoogleAccessTokenFromServerSecrets(),
        },
    },
})
```

The generated server runtime combines the build-time property identifier with the runtime-only
authorization callback before creating the Provider.
