---
title: Cloudflare
description: Understand the Traffic, Events, and Archive interfaces backed by Cloudflare services.
---

Cloudflare contributes three distinct capabilities. Web Analytics is a `traffic` Source,
Analytics Engine supplies event writes and an aggregate `product` Source, and R2 can back a
Nuxt archive mount. Configure only the interfaces the application uses.

| Capability | Cloudflare service                                 | SDK interface                                       |
| ---------- | -------------------------------------------------- | --------------------------------------------------- |
| Traffic    | Web Analytics GraphQL                              | `cloudflare()` Provider with a Web Analytics Source |
| Events     | Analytics Engine binding and SQL API               | Provider event destination and optional read Source |
| Archive    | Provider materializations plus optional R2 storage | Core archive and Nuxt R2 mount                      |

## Traffic

The Web Analytics Source is `cloudflare.web-analytics` in the `traffic` domain.

| Type       | Available values                                                        |
| ---------- | ----------------------------------------------------------------------- |
| Metrics    | `activeUsers`, `pageViews`, `visits`                                    |
| Dimensions | `time`, `browser`, `country`, `device`, `host`, `os`, `path`, `referer` |
| Reports    | Scalar totals, time series, and supported breakdown tables              |

You need an account ID, a server-side API token with Account Analytics read access, and the Web
Analytics site tag:

```ts
import { createAnalytics } from '@liria24/analytics'
import { cloudflare } from '@liria24/analytics/cloudflare'

const analytics = createAnalytics({
    name: 'website',
    providers: [
        cloudflare({
            accountId: process.env.CLOUDFLARE_ACCOUNT_ID!,
            apiToken: process.env.CLOUDFLARE_API_TOKEN!,
            webAnalytics: {
                host: 'analytics.liria.me',
                siteTag: process.env.CLOUDFLARE_SITE_TAG!,
            },
        }),
    ],
})
```

The Provider sends one account-scoped GraphQL request per compatible query group and filters it by
`siteTag`. Optional `host` permanently adds a `requestHost` filter, including when the query has
its own filters. It also changes the default Source ID to
`cloudflare.web-analytics:<hostname>` so archives from different hostnames cannot collide. An
explicit `sourceId` takes precedence. Cloudflare sampling intervals, partial GraphQL responses,
approximation, and warnings remain in report metadata. The SDK does not recreate Cloudflare's
browser beacon or visitor semantics.

`activeUsers` is a scalar-only estimate for a window of up to five minutes. Cloudflare Web
Analytics does not expose active sessions, so the Provider uses visits observed in that window and
marks the report approximate with a warning. This follows the common realtime-dashboard convention
of treating unique recent activity as online presence without claiming a persistent identity.

## Events

Analytics Engine has separate write and read interfaces.

### Write interface

A Workers binding provides an event destination:

```ts
import { cloudflareAnalyticsEngine } from '@liria24/analytics/cloudflare'

const engine = cloudflareAnalyticsEngine({
    binding: env.ANALYTICS,
})

await engine.eventDestination?.track(event)
```

Each validated event becomes one native data point. Event writes are not retried because replaying
a non-idempotent write could create duplicates.

### Read interface

Provide `accountId`, `apiToken`, and the native `dataset` name to enable SQL reads. The Source is
`cloudflare.analytics-engine.<dataset>` in the `product` domain.

| Type       | Available values                                   |
| ---------- | -------------------------------------------------- |
| Metric     | `events`                                           |
| Dimensions | `time`, `name`                                     |
| Reports    | Scalar count, time series, or event-name breakdown |

The Provider intentionally does not expose arbitrary blobs or doubles as a portable schema.
Sample-corrected counts remain marked approximate when the native sample interval is greater than
one.

Read requests retry transient `429`, `500`, `502`, `503`, and `504` responses at most twice.
`Retry-After` is respected when present. Permanent client errors and event writes are not retried.

## Archive

The Web Analytics Source declares a daily `pageViews` and `visits` materialization with a six-month
initial lookback. Analytics Engine declares daily event counts with a three-month lookback. Both
use a one-day finalization delay before completed monthly partitions are sealed.

Archive persistence is still a separate storage concern. In Nuxt, an R2 binding mounts the resolved
`archive.base`; the default is `analytics:archive`:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
    modules: ['@liria24/analytics/nuxt'],
    analytics: {
        name: 'website',
        archive: {
            base: 'my-archive',
            retention: '1y',
        },
        providers: {
            cloudflare: {
                r2: 'ANALYTICS_ARCHIVE',
            },
        },
    },
})
```

This maps `my-archive` to Nitro's `cloudflare-r2-binding` driver. An existing mount with that name
is preserved rather than overwritten.

## Nuxt configuration

Nuxt accepts resource identifiers at build time:

```ts [nuxt.config.ts]
analytics: {
    name: 'website',
    providers: {
        cloudflare: {
            analyticsEngine: 'ANALYTICS',
            webAnalytics: {
                host: 'analytics.liria.me',
                siteTag: 'your-site-tag',
            },
        },
    },
}
```

Web Analytics credentials stay in private runtime config or the `CLOUDFLARE_ACCOUNT_ID` and
`CLOUDFLARE_API_TOKEN` environment variables. Binding objects are resolved from the Cloudflare
request context at runtime.

If a configured provider identifier is missing, the Nuxt module warns and omits that capability.
Missing runtime credentials produce `AnalyticsError` with `CONFIGURATION_MISSING` when the Source
is queried; other configured Providers continue to work.
