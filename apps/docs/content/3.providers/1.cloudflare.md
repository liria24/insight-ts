## Web Analytics requirements

You need:

- **Account ID** — Cloudflare dashboard → account menu.
- **API token** — create a server-side token that can read Account Analytics.
- **Site tag** — Web Analytics → select the site → site configuration.

```ts
import { cloudflareWebAnalytics } from '@liria24/analytics/cloudflare'

const adapter = cloudflareWebAnalytics({
    accountId: process.env.CLOUDFLARE_ACCOUNT_ID!,
    apiToken: process.env.CLOUDFLARE_API_TOKEN!,
    siteTag: process.env.CLOUDFLARE_SITE_TAG!,
})
```

The adapter reads the account-scoped GraphQL dataset and filters it by `siteTag`. Keep the API
token in a server secret. If a query fails, verify the account ID, token permissions, site tag,
GraphQL errors, and Cloudflare rate-limit response.

## Analytics Engine requirements

For server writes you need an **Analytics Engine dataset binding** in the Worker or Nitro runtime.
For SQL queries you also need the **account ID**, an **API token** with Analytics Engine read
permission, and the **dataset name**.

```jsonc
{
    "analytics_engine_datasets": [
        {
            "binding": "ANALYTICS",
            "dataset": "website_events",
        },
    ],
}
```

The integration writes a fixed event envelope to the binding. It does not expose provider tokens
or native responses to the browser.

In Nuxt, `providers.cloudflare.analyticsEngine: 'ANALYTICS'` resolves that named binding from the
Cloudflare request context when the event relay runs. On runtimes where a binding is not available
there, wire the sink explicitly in `server/analytics.config.ts` as shown in the guide. R2 archive
bindings remain a Nitro Storage concern; `providers.cloudflare.r2: 'ANALYTICS_ARCHIVE'` registers
the named binding as the default archive mount without putting the binding object in module
options.

## Deploying these docs

The documentation app targets Cloudflare Workers through `apps/docs/wrangler.jsonc`. Before its
first deployment, create the `liria-analytics-docs-content` D1 database (or let the Cloudflare
deployment flow provision it) and ensure the `DB` binding resolves to that database. The checked-in
configuration declares `analytics.liria.me` as a custom domain but does not invent an account-specific
database ID or place credentials in source control.
