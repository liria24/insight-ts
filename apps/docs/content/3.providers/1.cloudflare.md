---
title: Cloudflare
description: Set up Web Analytics queries and Analytics Engine independently.
---

Use Cloudflare Web Analytics for traffic Metrics. Use Analytics Engine only when its native dataset
or Worker binding matches your application need; it is an independent Source and event destination.

## Web Analytics setup

```ts
import { createInsight } from 'insight-ts'
import { cloudflareWebAnalytics } from 'insight-ts/cloudflare'
import { defineProvider } from 'insight-ts/provider'

const cloudflare = defineProvider({
    id: 'cloudflare',
    sources: {
        webAnalytics: cloudflareWebAnalytics({ accountId, apiToken, host, siteTag }),
    },
})
const insight = createInsight({ providers: [cloudflare] as const })
```

## Query API

```ts
const dashboard = await insight.query((q) => ({
    traffic: q.source('cloudflare.webAnalytics', {
        dimensions: ['path'],
        limit: 20,
        metrics: ['pageViews', 'visits'],
        time: { ...range, grain: 'day' },
        where: { country: { in: ['JP', 'US'] } },
    }),
}))
```

Supported traffic breakdowns include path, referer, country, device, browser, host, operating
system, and time. Sampling is exposed as `sampled`, `sampleRate`, and `approximate`; capped rows
remain visible through partial quality warnings.

## Constraints

::warning
Cloudflare Web Analytics does not provide a native `activeUsers` metric. If your product displays a
recent-activity KPI, name it as an application KPI and query the native `visits` Metric over its own
short range.
::

`cloudflareAnalyticsEngine()` can expose a narrow Metric Source, a Worker-binding event sink, or
both. Dataset names, SQL capability, index and blob limits, and retention remain native to
Analytics Engine.

::collapsible{name="Why are the two Cloudflare APIs separate?"}
They have different storage and query models. Keeping them as separate Sources avoids implying that
their Metrics, quality signals, or event behavior are interchangeable.
::
